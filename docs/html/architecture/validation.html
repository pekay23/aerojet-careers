Architecture

Validation

The portal uses Zod for schema validation across client forms and server API routes.

02 · Client-side vs server-side

Client-side vs server-side

  • Client-side: React useEffect re-validates on every field change using safeParse(). Errors are stored in fieldErrors state and only shown after a field is touched (blur or submit attempt).
  • Server-side: API routes re-validate with the same Zod schemas before writing to the database. Server errors return 400 with a generic message.
03 · Touched-state pattern

Touched-state pattern

Form components (TextInput, Select, TextArea, FormField) accept an optional touched?: boolean prop. Validation feedback (red borders, error text) only renders when touched && error is true.

<FormField label="Email" error={errors.email} touched={!!touchedFields.email}>
  <TextInput error={errors.email} touched={!!touchedFields.email} onBlur={() => touch('email')} />
</FormField>

This prevents showing errors before the user has interacted with a field.

04 · Error message conventions

Error message conventions

Validation messages are friendly and actionable:

  • Text fields: "Input your first name", "Enter your last name"
  • Email: "Enter a valid email"
  • Selects: "Select your nationality"
  • Arrays: "Select at least one type rating"

Avoid generic messages like "Required" or "Invalid input".

05 · Refinements

Refinements

Custom refinements handle cross-field validation:

.superRefine((data, ctx) => {
  if (data.role_start_date && data.role_end_date && data.role_end_date < data.role_start_date) {
    ctx.addIssue({ code: z.ZodIssueCode.custom, message: 'End date must be after start date', path: ['role_end_date'] })
  }
})
